Dependências vulneráveis com Trivy

O terceiro portão de segurança: biblioteca com falha conhecida não entra na main. E o mapa completo da etapa 6.

O gitleaks olha para segredos, o Semgrep olha para o seu código. A etapa 6 olha para o código que não é seu: as bibliotecas do uv.lock e do package-lock.json. Essa análise se chama SCA (Software Composition Analysis) e é o que o glossário chama de proteção da cadeia de suprimentos.

A última linha da terceira coluna importa: o SCA pode deixar a main vermelha sem que ninguém tenha mexido em nada, porque o banco de avisos cresceu. Isso aconteceu no dia em que escrevi esta aula, e você vai ver abaixo. Um portão de SCA precisa de um plano para esse caso (a nota depois da prova, mais abaixo, trata disso).

O Trivy, no modo fs (sistema de arquivos), procura vulnerabilidades com base em arquivos de lock como Gemfile.lock e package-lock.json, e por padrão também procura segredos. (Trivy: Filesystem) O npm audit faz o equivalente só para npm: envia ao registro o nome e a lista de versões de cada pacote da árvore e recebe de volta os avisos. (npm-audit)

Repare que o Trivy também lê o package-lock.json. Ter os dois no front é redundância parcial: cada ferramenta consulta uma base diferente, e o plano pede as duas. Fica aberta a pergunta de se vale manter ambas; vamos medir isso na prova.

Parte 1: rode local e classifique

O Trivy não está instalado na sua máquina, mas o Docker está. Rode da raiz do projeto (o :Z é por causa do SELinux do Fedora, como nas suas notas; a primeira execução baixa ~130 MB do banco de vulnerabilidades):

docker run --rm -v "$PWD:/src:ro,Z" ghcr.io/aquasecurity/trivy:0.76.1 \
  fs --scanners vuln --severity HIGH,CRITICAL \
  --skip-dirs /src/.venv --skip-dirs /src/frontend/node_modules /src
cd frontend && npm audit --audit-level=high; echo "saída: $?"
PedaçoPara quê
fs … /srcVarre o diretório montado. Acha os dois lockfiles sozinho.
--scanners vulnSó vulnerabilidades. Segredos já são trabalho do gitleaks; dois donos para a mesma pergunta geram dois lugares para suprimir.
--severity HIGH,CRITICALFiltra o que aparece (e o que vale para o código de saída).
--skip-dirsEvita varrer o .venv e o node_modules da sua máquina. Na CI, o checkout limpo não os tem.
--audit-level=highDo npm audit: o nível mínimo de vulnerabilidade para sair com código diferente de zero. Não filtra o relatório, só o código de saída. (npm-audit)

Antes de abrir a resposta: o que apareceu? Para cada achado, anote a biblioteca, a severidade e se existe versão corrigida.

O que apareceu na minha rodada (22/10/2026)
  • npm: frontend/package-lock.json com 0 vulnerabilidades; o npm audit também deu 0 e saiu com 0.
  • Python: uv.lock com 1 CRITICAL: certifi 2026.7.22, aviso GHSA-6q48-6c7w-9gw2 ("certifi bundles emSign root CAs with compromised intermediate CA keys"), corrigido na 2026.10.19. O certifi é a lista de autoridades certificadoras em que o httpx confia para HTTPS: um problema nele é um problema na API que chama o Ollama/LLM.
  • O Trivy diz Suppressing dependencies for development and testing: por padrão ele ignora o grupo dev (pytest, ruff). Para incluir, a flag é --include-dev-deps.

Ou seja: se o job entrasse na CI hoje sem correção, nasceria vermelho. Daí o PR 1.

O identificador do aviso começa com GHSA (banco de avisos do GitHub); outros começam com CVE (o catálogo público de vulnerabilidades). Muitas falhas têm os dois.

Parte 2: PR 1, corrigir o certifi

Faça a correção numa branch, e confira o asterisco antes de commitar:

git switch main && git pull
git switch -c fix/certifi
git branch          # o * está em fix/certifi?
uv lock --upgrade-package certifi
git diff --stat     # só o uv.lock mudou?
git diff uv.lock    # só o certifi mudou de versão?

O --upgrade-package certifi atualiza só esse pacote dentro do que o pyproject.toml permite, sem mexer no resto. Testei numa cópia: o lock passou de 2026.7.22 para 2026.10.19 e o Trivy saiu com 0. Rode o Trivy de novo para conferir o seu, abra o PR e espere o backend verde: o uv sync --locked da CI confirma que o lock está consistente.

Parte 3: PR 2, os jobs no security.yml

Dois jobs novos em .github/workflows/security.yml, independentes: se o Trivy falhar, o npm audit ainda roda e você vê os dois resultados de uma vez. Como nas aulas anteriores, eu não escrevo o YAML: o roteiro está abaixo, e quando você mostrar o arquivo eu só aponto as linhas.

  1. Job trivy-fs em ubuntu-24.04, com permissions: contents: read. Nada de security-events: este job não envia SARIF.
  2. Checkout. Precisa de fetch-depth: 0? Pense no que o trivy fs lê: arquivos ou commits?
  3. A action do Trivy é a aquasecurity/trivy-action. Leia a seção abaixo (Fixe por SHA, não por tag) antes de escrever o uses.
  4. Entradas (with) da action, no mesmo item do uses: scan-type: fs, scan-ref: ., scanners: vuln, severity: HIGH,CRITICAL, exit-code: 1, ignore-unfixed: true e version: v0.76.1. Confirme cada nome no action.yaml da versão que você escolheu (repositório).
  5. Job npm-audit, com defaults.run.working-directory: frontend (você já usa isso no ci.yml). Sem npm ci: o npm audit lê o package-lock.json e consulta o registro. Eu não testei esse job no runner: se o log mostrar que falta o npm, acrescente o setup-node como no ci.yml.
  6. O comando: npm audit --audit-level=high. Pense em --omit=dev: auditar só o que vai para produção? A página do npm diz que tipos omitidos são pulados ao gerar o relatório. O que você perde e o que ganha?
  7. Antes do push: me mostre o arquivo. Abra o PR e espere os dois jobs verdes.
  8. Depois do verde: acrescente trivy-fs e npm-audit aos checks obrigatórios do protege-main. Lembre da regra dos nomes de job únicos entre workflows.

Fixe por SHA, não por tag

Em 19 de março de 2026, um atacante moveu 76 das 77 tags da trivy-action e as 7 tags da setup-trivy para commits maliciosos. O código roubava credenciais da memória do runner e rodava antes do scan de verdade, então os workflows pareciam normais. Quem usava uma tag executou código do atacante; quem usava o SHA de um commit anterior ao ataque, não. (Aqua: Trivy supply chain attack) A Aqua recomenda fixar por SHA de commit completo e imutável, e o guia de segurança do GitHub explica que uma tag pode ser movida ou apagada por quem ganhar acesso ao repositório da action. (GitHub: Secure use)

Isso é uma ironia que vale guardar: o scanner de segurança foi o vetor do ataque. Nenhuma ferramenta está acima da regra.

Como descobrir o SHA de uma tag, sem confiar em ninguém:

git ls-remote --tags https://github.com/aquasecurity/trivy-action 'v0.36.0*'

Vão aparecer duas linhas para a mesma tag: uma sem sufixo e outra terminando em ^{}. A tag v0.36.0 é anotada: a primeira linha é o SHA do objeto da tag, e a com ^{} é o SHA do commit para onde ela aponta. O que o uses: precisa é do commit. As tags leves (como a v0.35.0) têm só uma linha, e ela já é o commit.

Qual versão? A v0.36.0 foi publicada em 22/04/2026, depois do incidente, como release imutável. A Aqua cita a v0.35.0 (20/03/2026) como a versão sem problema. Qualquer uma serve; a aula usa a v0.36.0 porque ela mostra a tag anotada. Escreva o SHA e, na mesma linha, um comentário com a versão: uses: …@<sha> # v0.36.0. O comentário é para você e para o Dependabot (aula 0005).

Para conferir o seu SHA (abra depois de achar)

O commit da v0.36.0 começa com ed142fd. Se o seu começa com a9c7b0f, você pegou o objeto da tag, não o commit.

Duas decisões que ficam registradas: ignore-unfixed: true faz o portão ignorar falhas que ainda não têm versão corrigida, porque você não tem como agir sobre elas; o custo é que elas deixam de aparecer. E version: v0.76.1 fixa o binário do Trivy, que é outro elo da cadeia: o padrão da action na v0.36.0 é a v0.70.0, e eu testei a 0.76.1.

Prove o portão

O plano diz: "PR adicionando uma versão antiga e vulnerável de alguma biblioteca → pipeline falha." Com os dois jobs obrigatórios e o PR 2 mesclado, faça duas provas, uma por job. Cada uma numa branch própria, a partir da main atualizada. Não mescle nenhuma.

ProvaO que fazerQuem deve ficar vermelho
PythonEm pyproject.toml, acrescente "pyyaml==5.3" às dependências e rode uv locktrivy-fs (2 CRITICAL: CVE-2020-14343 e CVE-2020-1747)
npmEm frontend/: npm install lodash@4.17.20npm-audit (1 HIGH, "Command Injection in lodash") e, talvez, o trivy-fs

Testei os dois cenários numa cópia, fora do repositório: o pyyaml==5.3 faz o Trivy sair com 1; o lodash@4.17.20 faz o npm audit sair com 1. Antes de olhar o PR da prova do npm, aposte: o trivy-fs também vai ficar vermelho? Depois confira e anote o resultado, porque ele responde se vale manter as duas ferramentas no front.

Tire o print de cada PR (job vermelho, merge bloqueado), feche sem mesclar e apague as branches. Esses prints são a evidência do currículo.

E se o portão ficar vermelho na main sem ninguém ter mexido? É o caso do certifi. A resposta madura tem três partes: (1) atualizar a biblioteca, que é o normal; (2) se não houver versão corrigida, o ignore-unfixed já cobre; (3) se for um falso positivo, ignorar aquele aviso com justificativa (no Trivy, um arquivo .trivyignore com o id). Desligar o portão não está na lista.
