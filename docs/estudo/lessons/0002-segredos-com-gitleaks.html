Segredos com gitleaks

O primeiro portão de segurança: nenhuma chave entra na main.

Na aula 0001, a CI virou portão. Até aqui, porém, ela só verifica qualidade: lint, testes e build. A etapa 4 abre o Bloco B com a pergunta mais barata de responder e mais cara de errar: tem alguma senha ou chave neste código?

Por que apagar não resolve

O Git guarda cada versão de cada arquivo. Se uma chave entrou no commit A e foi apagada no commit B, ela continua inteira em A, e qualquer pessoa que clonar o repositório consegue lê-la com git log -p. O seu repositório é público.

commit A: adiciona a chave→commit B: apaga a chave→A continua no histórico

A documentação do GitHub é direta: fazer um novo commit, ou apagar e recriar o repositório, não impede que o segredo seja explorado. Todo segredo vazado deve ser tratado como comprometido imediatamente, e revogar a chave no provedor é o passo de correção mais importante. (Remediating a leaked secret) Reescrever o histórico vem depois, se vier, porque exige force push. E lembre que o seu ruleset bloqueia force push.

A regra que fica: segredo vazado → revoga primeiro, limpa depois. É por isso que o portão precisa barrar antes do merge: depois, o estrago já está feito.

O que é o gitleaks

O gitleaks procura segredos (senhas, chaves de API, tokens) em repositórios Git, em arquivos ou no texto que você passar pela entrada padrão. Ele tem três modos: git, dir e stdin. Os comandos antigos detect e protect foram descontinuados na v8.19.0. (README do gitleaks) Cada tipo de segredo é uma regra: uma expressão regular, mais um limite de entropia (o quanto o texto parece aleatório), mais uma lista de exceções.

Você vai usá-lo de dois jeitos, e cada um cobre um buraco do outro:

UsoO que analisaPor quê
Varredura única, na sua máquina Todo o histórico, de todas as branches Descobre se já vazou algo. O job do PR não olha para trás.
Job na CI, a gitleaks-action Só os commits do PR (no push, só os commits enviados) Impede que algo novo entre. A action pega a lista de commits do PR pela API e analisa só esse intervalo. (gitleaks.js)

Isso segue o que o plano pede para todo o Bloco B: primeiro relatório, depois portão. A varredura é o relatório; o job, o portão.

Parte 1: varredura do histórico

Rode na raiz do projeto. A imagem oficial está no GHCR. (README)

docker run --rm -v "$PWD":/repo:Z ghcr.io/gitleaks/gitleaks:v8.30.1 \
  git /repo --log-opts="--all" --redact -v
PedaçoPara quê
:ZSeu Fedora usa SELinux, que bloqueia o container de ler a pasta montada sem esse rótulo.
v8.30.1A versão fixada, a mesma que você vai usar na CI. latest mudaria sem aviso.
--log-opts="--all"Repassado ao git log -p: inclui todas as branches, não só a atual.
--redactEsconde o valor do segredo na saída. Assim o print para o currículo não vaza nada.

Código de saída: 0 significa nada encontrado; 1 significa achado (ou erro). (README) Confira com echo $? logo depois.

Se aparecer algo

  • É um segredo real (por exemplo, uma senha que você usa em outro lugar): revogue ou troque no serviço antes de qualquer outra coisa. Depois, me chame para decidirmos juntos se vale reescrever o histórico.
  • É falso positivo (um valor de teste, como a senha edurag do Postgres descartável da CI): copie o Fingerprint do achado para um arquivo .gitleaksignore na raiz, um por linha, com um comentário # explicando o motivo. Esse é o mesmo princípio da etapa 5: suprimir só com justificativa. (README, seção .gitleaksignore)

Parte 2: o job na CI

Agora é você quem escreve. Crie .github/workflows/security.yml, um arquivo novo, porque os próximos portões do Bloco B (Semgrep, Trivy) vão morar nele. A seguir estão os requisitos. As peças vêm do README da action.

  1. Mesmos gatilhos do ci.yml. push e pull_request na main.
  2. Um job com id gitleaks em ubuntu-24.04. O id precisa ser único entre os workflows, porque vai virar check obrigatório.
  3. Checkout com fetch-depth: 0. O padrão baixa só o último commit. Sem o histórico, o intervalo de commits do PR não existe na máquina e a análise falha.
  4. O step da action: gitleaks/gitleaks-action@v3.0.0. A v3 roda em Node 24; a v2 roda em Node 20, que sai dos runners do GitHub em 16/09/2026. (releases)
  5. Variável GITHUB_TOKEN vinda de secrets.GITHUB_TOKEN. Sem ela, a análise de PR encerra com erro. Ela é criada pelo GitHub em cada execução, então você não cadastra nada.
  6. Sem GITLEAKS_LICENSE. A licença só é exigida para repositórios de organização; o seu é de conta pessoal. (README da action)
  7. Variável GITLEAKS_VERSION: 8.30.1, sem o v. Fixa a mesma versão da varredura local.
  8. Bloco permissions no job: contents: read (ler o código) e pull-requests: write (a action comenta no PR, na linha do achado). Declarar só o que o job usa é o menor privilégio; a etapa 6 volta a esse ponto. (Automatic token authentication)

Quando terminar, me mostre o arquivo antes do push. Eu reviso e explico o que estiver estranho, mas não escrevo por você.

Do job ao portão

Abra o PR. Quando o job gitleaks ficar verde, vá ao ruleset protege-main e adicione gitleaks aos status checks obrigatórios. Sem esse passo, o job só avisa, como era a CI antes da aula 0001.

Prove o portão

O plano diz: "PR com uma chave falsa no formato de chave da AWS → pipeline falha."

Armadilha: não use a chave de exemplo da documentação da AWS, AKIAIOSFODNN7EXAMPLE. A regra aws-access-token tem uma exceção para qualquer valor que termine em EXAMPLE. Com ela, o PR passaria verde e a prova não provaria nada. (gitleaks.toml)

A regra procura AKIA seguido de 16 caracteres entre A–Z e 2–7, com entropia mínima de 3. Gere um valor aleatório, que não é chave de ninguém:

git switch main && git pull
git switch -c teste/segredo-falso
echo "AWS_ACCESS_KEY_ID=AKIA$(tr -dc 'A-Z2-7' </dev/urandom | head -c16)" > config-falsa.env
git add config-falsa.env
git commit -m "teste: chave falsa para provar o gitleaks"
git push -u origin teste/segredo-falso

Abra o PR. O job gitleaks deve ficar vermelho, com um comentário na linha da chave, e o merge deve ficar bloqueado. Tire o print, feche o PR sem mesclar e apague a branch.

Observe a lição de novo: mesmo com o PR fechado e a branch apagada, o commit continua acessível na aba Commits do PR fechado. Com uma chave falsa, isso não tem problema. Com uma real, seria um vazamento. Por isso o portão precisa existir.

Recupere da memória

Responda sem voltar ao texto.

1. Por que um segredo apagado num commit posterior continua vazado?

2. Você descobre uma chave real no histórico. Qual é o primeiro passo?

3. Por que a chave AKIAIOSFODNN7EXAMPLE não serve para a prova?

4. Para que serve fetch-depth: 0 no checkout do job?

5. O job gitleaks está verde no PR. O que falta para ele virar portão?
