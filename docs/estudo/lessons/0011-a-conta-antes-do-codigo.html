Por que código, num ambiente que vai morrer?

Justamente porque vai morrer. Na etapa 15, um terraform destroy apaga tudo o que o Terraform criou. Recurso criado à mão no console fica esquecido e continua cobrando. Por isso, a regra da etapa é: o que custa dinheiro nasce pelo Terraform. À mão, só o que vem antes dele (esta aula e o bucket do state na 0012).

PeçaO que éNo EduRAG
ProviderO plugin que fala com a API de um serviçohashicorp/aws, fixado por versão

O state é o que liga cada objeto real ao seu bloco no código. Por padrão, ele fica num arquivo local chamado terraform.tfstate, e a documentação desaconselha esse arquivo local para quem trabalha com outras pessoas ou máquinas. (Terraform: State) No EduRAG, a CI da aula 0014 é a "outra máquina". E o state é sensível: "o Terraform guarda o state num arquivo de texto puro, que inclui qualquer valor secreto definido na configuração". (Terraform: Manage sensitive data) Daí a regra da trilha: a chave do Claude e as senhas vão para o Parameter Store pelo aws ssm put-parameter, à mão, e nunca entram num recurso.

A instância parada (stop) não cobra hora de uso, mas o disco EBS continua cobrando. O IPv4 público automático é devolvido no stop, e um novo vem no start. (EC2: How stop and start works) Então a conta de quem estuda 8 horas por dia, 30 dias, é: 240 h × 0,0416 + 240 h × 0,005 + 1,60 ≈ US$ 12,80. Ligada o mês todo, ≈ US$ 35,60.

Aposte: se você esquecer a máquina ligada num fim de semana, quanto custa? E se der terraform destroy na sexta, o que ainda cobra na segunda?

Resposta

Sexta 18h a segunda 8h são 62 h: 62 × (0,0416 + 0,005) ≈ US$ 2,90. Depois do destroy, só sobra o que ficou fora do Terraform: o bucket do state (centavos) e o Budget (grátis). Esse é o motivo de quase tudo nascer pelo Terraform.

Decisão: qual é o plano da sua conta?

Contas criadas a partir de 15/07/2025 escolhem entre o plano gratuito e o pago. O gratuito dá até US$ 200 em créditos e dura 6 meses ou até os créditos acabarem, o que vier primeiro. Ele não deixa passar do limite. (EC2: Free Tier usage · AWS Free Tier) Isso muda duas coisas nesta etapa:

Plano gratuitoPlano pago
IAM Identity CenterAtivar a instância de organização cria uma AWS Organization. Isso passa a conta para o plano pago, e os créditos expiram na hora.Funciona, mas cria uma Organization só para uma pessoa.
Tipo da instânciaSó os elegíveis: t3.micro, t3.small, t4g.micro, t4g.small, c7i-flex.large, m7i-flex.large. O t3.medium do plano não está na lista.Qualquer tipo, pagando.

Fontes: Enable IAM Identity Center ("If you use a free tier account, creating an AWS organization automatically upgrades your account to a paid plan… Your free tier credits expire immediately.") · EC2: Free Tier usage

Recomendo, nos dois planos: usuário IAM com MFA e aws login, sem Identity Center. O aws login usa o seu login do console para entregar credenciais temporárias, válidas por até 12 horas, sem access key no disco. A documentação o chama de método recomendado para quem usa root ou usuário IAM. (AWS Sign-In: Sign in through the AWS CLI) O Identity Center é o padrão de empresas com várias contas. Aqui ele não traz ganho, e no plano gratuito custaria os créditos. A troca da instância (t3.medium × m7i-flex.large, que é elegível) fica para a aula 0013, com a RAM medida.

Se a sua conta foi criada pelo "Sign up for AWS (new)", com projects: pare e me conte antes de seguir. Nessa experiência, a AWS gerencia políticas da conta, e o Identity Center e o Organizations ficam de fora. (Supported services for Sign up for AWS (new))

Que permissão dar ao seu usuário?

Nas aulas 0012 a 0014, o seu usuário vai criar bucket, EC2, roles, instance profile e o provedor OIDC. A política gerenciada PowerUserAccess não serve, porque não gerencia o IAM, e roles fazem parte do IAM. Por isso, o usuário do dia a dia recebe AdministratorAccess e, para o aws login, a SignInLocalDevelopmentAccess. (AWS Sign-In)

Isso contradiz o menor privilégio? Não, porque a conta inteira é sua e o usuário existe para administrá-la. O que segura o risco é o MFA e a credencial que expira. O menor privilégio de verdade vale para as identidades de máquina, a instância e a CI, e é escrito por você nas aulas 0013 e 0014. O root fica para as tarefas que só ele faz, sempre com MFA e sem access key. (IAM: Root user best practices)

Mão na massa

Sem esqueleto: hoje não há HCL. São cliques no console e instalações. Anote o que você escolher; o nome do Budget volta na aula 0014.

  1. Plano da conta: entre como root e veja, na área de Billing, se a conta está no plano gratuito (com créditos) ou no pago. Se não tiver conta, crie uma, e no cadastro anote qual plano escolheu.
  2. Root: em Security credentials, registre um MFA (chave de acesso ou app autenticador). Na mesma tela, confira que não há access key do root. Se houver, apague. (Root user best practices)
  3. Budget, antes de qualquer recurso: Billing and Cost Management → Budgets → Create budget, modelo Monthly cost budget. Nome edurag-mensal, valor US$ 15 (a conta de 8 h/dia acima, com folga), seu e-mail. Confira na tela quais alertas o modelo criou (real e previsto) e em que percentuais. (AWS Budgets: Create a budget)
  4. Usuário IAM: IAM → Users → Create user, com acesso ao console e senha própria. Políticas: AdministratorAccess e SignInLocalDevelopmentAccess. Não crie access key. Depois, em Security credentials do usuário, registre o MFA.
  5. Teste o usuário: saia do root e entre pela URL de login da conta com o usuário novo e o MFA. Daqui para frente, o root só volta para tarefa de root.
  6. AWS CLI v2 (PowerShell como administrador): msiexec.exe /i https://awscli.amazonaws.com/AWSCLIV2.msi. Feche e reabra o terminal. aws --version precisa mostrar aws-cli/2.32.0 ou mais nova. (AWS CLI: Install)
  7. Perfil e login: aws configure set region us-east-1 --profile edurag, depois aws login --profile edurag. O navegador abre; entre com o usuário IAM, e não com o root.
  8. A prova da identidade: aws sts get-caller-identity --profile edurag. O Arn precisa terminar em :user/<seu-usuário>. Se terminar em :root, você entrou com o root: aws logout --profile edurag e repita.
  9. Terraform 1.17.2: em releases.hashicorp.com/terraform/1.17.2, baixe o terraform_1.17.2_windows_amd64.zip e o terraform_1.17.2_SHA256SUMS. Compare o Get-FileHash .\terraform_1.17.2_windows_amd64.zip com a linha windows_amd64 do arquivo de somas. Os dois têm que ser iguais. Extraia o terraform.exe numa pasta sua (por exemplo C:\tools\terraform) e acrescente essa pasta ao Path do usuário (Variáveis de ambiente). Reabra o terminal: terraform version. (Terraform: Install)
  10. Plugin do Session Manager: rode o instalador SessionManagerPluginSetup.exe do link oficial e deixe a pasta padrão. Reabra o terminal e rode session-manager-plugin. A resposta esperada é "The Session Manager plugin is installed successfully. Use the AWS CLI to start a session." (Install on Windows · Verify)
  11. Nada no repositório: git status limpo. Credenciais do aws login ficam no cache da CLI, no seu perfil do Windows, fora do projeto.

Para o Terraform ler o aws login (aula 0012): nas pastas do projeto, use $env:AWS_PROFILE = "edurag" na sessão do PowerShell. Um artigo da Classmethod testou que o provider lê essa credencial a partir da 6.23.0 e o backend S3 a partir do Terraform 1.15.0. As versões de hoje passam das duas. Essa fonte não é oficial: se o init der "No valid credential sources found", me chame. (Classmethod: S3 backend e aws login · provider-aws #45316)
