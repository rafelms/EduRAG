Build e scan de imagens

O último portão do Bloco B: a imagem só passa se construir, estiver limpa de CRITICAL e não rodar como root.

Pré-requisito (atualizado em 28/10): a etapa 7 dependia de duas coisas da etapa 6, e as duas estão feitas: actions fixadas por SHA (PR #17) e o uv novo no Dockerfile (PR #29: uv:0.13.1 fixado por digest e uv sync --locked). O que sobrou da etapa 6, o cooldown no pyproject.toml a partir de 30/10, não toca em nenhum arquivo desta etapa. As duas andam em paralelo.

O que esta etapa faz

Até agora a pipeline verificou texto: segredos, código, lockfiles. A etapa 7 verifica o artefato que vai para a AWS: a imagem. É nela que mora o que o uv.lock não mostra: o sistema operacional da imagem base (Debian, Alpine), o nginx e o usuário que executa o processo.

Você já sentiu falta deste portão. Na primeira rodada do Dependabot (registro 0007), os PRs #19 e #20 trocaram as imagens base do front e ficaram verdes sem que nenhum check construísse o Dockerfile. A conferência foi feita à mão. Depois desta etapa, um PR desses só fica verde se a imagem construir, não tiver CRITICAL e não rodar como root.

Em uma frase: construir cada imagem na CI, escanear e barrar o PR se ela falhar. Ainda não publica nada. Publicar é a etapa 8.

O que o Trivy vê dentro de uma imagem

O trivy image faz duas varreduras: os pacotes do sistema operacional (casados pela distribuição, como Debian ou Alpine) e os pacotes de linguagem (como os do Python). Por padrão ele procura a imagem no Docker local, antes de tentar um registro. (Trivy: Container Image)

Medi as duas imagens do projeto em 23/10/2026, com o Trivy 0.76.1. Esta tabela está desatualizada de propósito: depois dela, o Dependabot trocou a base do front para nginx-unprivileged:1.31-alpine e o estágio de build para node:26-alpine (PRs #19 e #20). Em 28/10 o front já estava com 92 MB, e os uids continuam 10001 e 101. As vulnerabilidades você mede na Parte 1.

Aposte antes de seguir: o front final só tem o nginx e os arquivos estáticos. O Node, o npm e o node_modules do estágio de build aparecem no scan? Dica: olhe os dois FROM do frontend/Dockerfile.

Resposta

Não aparecem. O Dockerfile é multi-stage: o estágio builder (node:26-alpine, desde o PR #20) gera o dist/, e só essa pasta é copiada (COPY --from=builder) para o estágio final. A imagem entregue é a do último FROM. O mesmo vale para o api: o uv fica no estágio de build e a imagem final nem o tem (está no comentário do seu Dockerfile).

Parte 1: rode local primeiro

Regra do Bloco B: relatório antes de portão. Construa e escaneie à mão, na raiz do projeto:

PedaçoPara quê

Parte 2: PR 1, o job imagem-api

Arquivo novo: .github/workflows/build.yml, com name: Build e os mesmos gatilhos dos outros workflows. O id do job é imagem-api. Nas etapas anteriores o ponto fraco foi a estrutura, então desta vez vai um esqueleto: as chaves, sem os valores. Você preenche.

name: Build

on:
  # os mesmos gatilhos do security.yml

jobs:
  imagem-api:
    runs-on: …
    permissions:
      …
    steps:
      - uses: …            # checkout
      - uses: …            # setup-buildx
      - name: …
        uses: …            # build-push-action
        with:
          …
      - name: …
        uses: …            # trivy-action
        with:
          …
      - name: …
        run: …             # checagem de não-root
  1. Gatilhos e permissões. Os mesmos de push/pull_request na main. As permissions mínimas: este job lê o código e mais nada.
  2. Fixe cada action por SHA desde já (aula 0005; o commit da linha ^{} se for tag anotada). Você precisa de três: actions/checkout, docker/setup-buildx-action e docker/build-push-action. Os exemplos das documentações usam v4 para o buildx e v7 para o build-push, mas confirme as versões no ls-remote.
  3. Buildx. O setup-buildx-action usa por padrão o driver docker-container, que é o que permite exportar cache. (setup-buildx-action)
  4. Build. Entradas da build-push-action: context: ., push: false e load: true, além de uma tags (ex.: edurag-api:ci). O load é atalho para --output=type=docker: carrega a imagem no Docker do runner, onde o Trivy a procura. O push manda a um registro. (build-push-action) Sem o load, a imagem some no fim do build e não há o que escanear.
  5. Cache. cache-from: type=gha,scope=api e cache-to: type=gha,mode=max,scope=api. Cada imagem precisa do seu scope: builds que dividem o mesmo escopo sobrescrevem o cache um do outro. (Docker: GitHub Actions cache) O cache só é lido da branch atual, da base e da padrão, então o primeiro PR de uma branch nova constrói tudo do zero.
  6. Trivy. A trivy-action (a mesma SHA do security.yml) com scan-type: image e image-ref igual à tag do build. Reaproveite as entradas da aula 0004 (scanners: vuln, exit-code: '1', ignore-unfixed, version) e troque o severity pelo que o plano pede.
  7. Não-root. Um step run que executa id -u na imagem e falha se o resultado for 0. Pense em como um test do shell compara texto, e lembre da Parte 1: o comando que imprime o uid.
  8. Antes do push: me mostre o arquivo. Abra o PR e espere o job verde. Observe o tempo; depois, rode o PR de novo (Re-run) e compare: o segundo build deve usar o cache.

Duas coisas que o job não faz, de propósito: não publica a imagem (push: false; o GHCR é a etapa 8) e não envia SARIF. O objetivo desta etapa é o portão. A etapa 8 vai reaproveitar o cache e só publicar o que passou por aqui, que é o "pronto quando" do plano: as imagens só existem se passaram no scan.

Parte 3: PR 2, o job imagem-front

Mesma estrutura, agora sem esqueleto: copie o job do api e decida o que muda. Pistas: o Dockerfile do front não está na raiz; o scope do cache; a tag; e o nome do job. Depois do verde, acrescente imagem-api e imagem-front aos checks obrigatórios do protege-main (os nomes só aparecem na busca depois de terem rodado).

Desafio opcional: os dois jobs ficaram quase iguais. O GitHub Actions tem matrix para isso. Antes de refatorar, pense no custo: o nome do check obrigatório muda (ele passa a incluir o valor da matriz), então o ruleset também. Se refatorar, confira o nome exato na lista do ruleset, que eu não testei.

Prove os dois portões

São dois bloqueios diferentes, então são duas provas, cada uma numa branch a partir da main atualizada. Não mescle nenhuma.

ProvaO que fazerQuem deve ficar vermelho
Imagem vulnerávelEm frontend/Dockerfile, troque a base final de nginx-unprivileged:1.31-alpine para nginx-unprivileged:1.21-alpineimagem-front, no step do Trivy (Alpine 3.15.4, fim de suporte; 9 CRITICAL, todos com correção)
Imagem rootEm Dockerfile, comente a linha USER eduragimagem-api, no step do não-root (o id -u devolve 0)

Testei as duas antes: o front com a base 1.21 constrói e sobe como uid 101, e o scan acha os 9 CRITICAL; e uma imagem sem USER devolve 0 no id -u. Ou seja, cada job cai pelo motivo certo. Confirme isso no log antes do print: vermelho pelo motivo errado não vale (o PR #14 da aula 0004 mostrou isso).

Por que a prova do api não troca a base para python:3.9: eu testei essa base e ela tem CRITICAL, mas o projeto exige Python 3.12 (requires-python), então o uv sync do build quebraria antes do scan. O job ficaria vermelho, só que no step do build, e não no que você quer provar.

Tire o print de cada PR (job vermelho, Required, merge bloqueado), feche sem mesclar e volte à main (git switch main && git pull, e apague a branch local com -D).
