SAST com Semgrep

O segundo portão de segurança: código perigoso não entra na main, e cada achado aparece na aba Security.

Na aula 0002, o gitleaks passou a responder "tem chave neste código?". A etapa 5 faz uma pergunta mais difícil: "este código tem um jeito conhecido de ser atacado?" O exemplo clássico, e a prova desta aula, é o SQL montado por concatenação de strings.

SAST × DAST

A OWASP chama as ferramentas de análise de código-fonte de SAST (Static Application Security Testing): elas examinam o código, sem executá-lo, em busca de falhas de segurança. Já os scanners de aplicação web, os DAST (Dynamic), analisam a aplicação normalmente de fora, com ela rodando. (OWASP: Source Code Analysis Tools · OWASP: Vulnerability Scanning Tools)

SAST (esta aula)DAST
Olha paraO código-fonteA aplicação rodando
Quando rodaEm todo PR, antes do buildDepois do deploy num ambiente de teste
MostraArquivo, linha e trechoA URL e a requisição que funcionou
Ponto fracoMuitos falsos positivos; não vê configuraçãoNão diz em que linha está o erro

A OWASP aponta, entre os pontos fortes do SAST, que ele roda bem em CI e encontra com confiança problemas conhecidos como SQL injection. Entre os fracos, estão os falsos positivos e o fato de ele pegar só uma pequena parte das falhas. (OWASP) Por isso o SAST é um portão, não a defesa inteira.

O que é o Semgrep

O Semgrep lê o código e compara com regras. Cada regra é um padrão de código (não uma regex de texto, como no gitleaks) com uma severidade e uma mensagem. As regras vêm em conjuntos de regras do Semgrep no registro público, como p/default e p/python. (CLI reference)

Cuidado com o nome: o Semgrep chama os conjuntos de regras de rulesets, mas não têm nada a ver com o ruleset protege-main do GitHub. Nesta trilha, ruleset é sempre o do GitHub, e o do Semgrep é conjunto de regras. Veja o glossário.

Testei os conjuntos antes de escrever esta aula, com o Semgrep 1.180.0, num arquivo com duas consultas vulneráveis:

Códigop/pythonp/default
session.execute("..." + nome)não apontousqlalchemy-execute-raw-query
session.execute(text(sql)), com sql concatenadoavoid-sqlalchemy-textavoid-sqlalchemy-text

Por isso a aula usa o p/default: ele cobre mais casos e, no mesmo scan, inclui regras de Python, TypeScript e YAML do GitHub Actions. A regra sqlalchemy-execute-raw-query é classificada como CWE-89 (SQL injection) e recomenda o text() com parâmetros nomeados. (regra no semgrep-rules)

SARIF: o formato da aba Security

O SARIF é um formato JSON padronizado para resultados de análise estática. A aba Security → Code scanning do GitHub aceita SARIF de ferramentas de terceiros, e a code scanning só exige licença em repositórios privados; o seu é público. (About code scanning) O envio é feito pela action github/codeql-action/upload-sarif@v4, e o job precisa da permissão security-events: write, que a documentação diz ser obrigatória para todos os workflows de envio. (Uploading a SARIF file)

Semgrep gera semgrep.sarif→upload-sarif envia→aba Security + anotações no PR

A regra do Bloco B é: rodar em modo de relatório, entender o que aparece e só depois virar portão. Rode na raiz do projeto, com a mesma versão que vai na CI:

Minha classificação (abra depois de fazer a sua)

Na minha rodada, em 20/10/2026, apareceram 8 achados e nenhum no código da aplicação. O text("SELECT 1") do /ready não foi apontado, porque é uma string fixa.

  • 7 × github-actions-mutable-action-tag (WARNING): actions referenciadas por tag, como @v7. É exatamente o item "fixar as actions por SHA" da etapa 6.
  • 1 × uv-missing-dependency-cooldown (MEDIUM): o pyproject.toml não manda o uv esperar alguns dias antes de aceitar pacotes recém-publicados. Também é cadeia de suprimentos, também da etapa 6.

Conclusão: se o portão barrasse qualquer achado, ele ficaria vermelho hoje por causa de trabalho que o plano reserva para a etapa seguinte. Daí o desenho da Parte 2.

Trade-off que fica registrado: fixar o Semgrep em 1.180.0 fixa o motor, mas o p/default é baixado do registro a cada execução, então as regras podem mudar sem você mexer em nada. Se um dia o job ficar vermelho "do nada", a primeira hipótese é uma regra nova.

Parte 2: o job na CI

O job vai em .github/workflows/security.yml, ao lado do gitleaks. O desenho é este: tudo vai para a aba Security, mas só severidade ERROR bloqueia. Os 8 avisos ficam visíveis lá como lista de tarefas da etapa 6.

  1. Um job com id semgrep em ubuntu-24.04, no mesmo arquivo e com os mesmos gatilhos.
  2. Bloco permissions: contents: read e security-events: write. Este job não comenta no PR, então não precisa de pull-requests.
  3. Checkout. Precisa de fetch-depth: 0? Decida sozinho. (É a pergunta 2 do quiz.)
  4. Instalar o uv com a mesma action do ci.yml.
  5. Step "relatório": o comando da Parte 1, acrescentando --sarif-output=semgrep.sarif. Sem --error, ele sai com 0 mesmo com achados. (CLI reference, exit codes)
  6. Step de envio: github/codeql-action/upload-sarif@v4, com o parâmetro sarif_file: semgrep.sarif. O parâmetro category é opcional e serve para separar resultados de ferramentas diferentes.
  7. Step "portão": o mesmo comando, agora com --severity ERROR --error. Com --error, o Semgrep sai com 1 quando há achado, e o step fica vermelho.
  8. Confira a ordem. Os steps rodam em sequência, e um step que falha impede os seguintes (está nas suas anotações). Em que ordem o envio e o portão precisam ficar?

Atenção à estrutura YAML (o tropeço da etapa 4): cada step é um item da lista, começando com -. O uses e o with de uma action ficam no mesmo item, com o with alinhado ao uses. Desta vez eu aponto as linhas com erro e você corrige.

Quando terminar, me mostre o arquivo antes do push. Depois, abra o PR. Com o job semgrep verde, adicione semgrep aos checks obrigatórios do protege-main. Depois do merge, confira a aba Security → Code scanning: os 8 avisos devem estar lá.

Prove o portão

O plano diz: "PR com SQL montado por concatenação de string → apontado." Crie um arquivo à parte, para não mexer no código de verdade:

git switch main && git pull
git switch -c teste/sql-concatenado

Em app/teste_sast.py:

from sqlalchemy import Result, text
from sqlalchemy.orm import Session


def buscar_por_nome(session: Session, nome: str) -> Result:
    sql = "SELECT * FROM documents WHERE filename = '" + nome + "'"
    return session.execute(text(sql))

Testei esse arquivo com a configuração do projeto (uv run ruff check, que lê o pyproject.toml): o ruff check e o ruff format --check passam, e o Semgrep sai com 1 apontando avoid-sqlalchemy-text. Ou seja, só o semgrep deve ficar vermelho. Commit, push, PR. Espere o job vermelho, a anotação na linha 7 e o merge bloqueado. Tire o print, feche o PR sem mesclar e apague a branch.

Por que os tipos: o projeto liga as regras ANN do ruff (anotação de tipo obrigatória fora de tests/). A primeira versão desta aula não tinha tipos e derrubava também o backend, porque eu tinha testado com o ruff sem o pyproject.toml. Lição de prova: teste sempre com a mesma configuração que a CI usa.

Não ponha o arquivo em tests/: o Semgrep ignora essa pasta por padrão (são os 11 arquivos do Scan skipped), e a prova passaria verde sem ele ter olhado.

Repare: um nome como x' OR '1'='1 faria essa consulta devolver todos os documentos. A versão segura é a que a regra recomenda: text("... WHERE filename = :nome"), passando {"nome": nome} à parte. O banco recebe o valor separado do comando e nunca o interpreta como SQL.

E se um achado for falso positivo?

Mesmo princípio da etapa 4: suprimir só com justificativa. No Semgrep, isso é um comentário # nosemgrep: <id-da-regra> na linha do achado ou na anterior. Sempre com o id, para não silenciar outras regras. (Ignore files, folders, and code) A sintaxe não tem campo de motivo, então escreva o porquê num comentário ao lado. O .semgrepignore serve para pular arquivos inteiros e é uma arma grande demais para um achado só.
