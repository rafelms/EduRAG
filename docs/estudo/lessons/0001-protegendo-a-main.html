Protegendo a main

A CI passa de aviso a portão.

O problema

Hoje o seu ci.yml roda os jobs backend e frontend em todo PR. Mas ele só informa. Se o pytest falhar, o botão Merge continua verde, e um git push origin main direto nem passa por PR. A CI vira um conselho que dá para ignorar.

branch de trabalho→PR→backend + frontend→ruleset da main→merge

Um ruleset é a peça que transforma o resultado da CI em uma condição para o merge. É uma lista nomeada de regras que o GitHub aplica a branches que você escolher. (About rulesets)

Ruleset ou proteção de branch clássica? As duas resolvem o problema. Use o ruleset, que é o modelo mais novo: você pode ter vários ao mesmo tempo, eles se somam (vale sempre a regra mais restritiva), dá para desativar sem apagar, e qualquer pessoa com acesso de leitura consegue ver as regras ativas. (About rulesets)

As quatro regras e o porquê de cada uma

RegraValorPor quê
Restrict deletionsligada Ninguém apaga a main por acidente.
Block force pushesligada Um push --force reescreve o histórico e pode apagar commits. (Available rules)
Require a pull request before mergingligada, 0 aprovações Acaba com o push direto. Zero aprovações porque o autor de um PR não pode aprovar o próprio PR: com 1, você ficaria preso sozinho. (Approving a PR)
Require status checks to passbackend e frontend É aqui que a CI vira portão. Os nomes são os ids dos jobs no ci.yml. Por isso o GitHub pede nomes de job únicos entre os workflows. (About protected branches)

Duas armadilhas

  • O ruleset nasce desativado. O status padrão é Disabled. Se você esquecer de mudar para Active, nada é aplicado. (Creating rulesets)
  • Você é admin. Quem está na bypass list passa por cima das regras. Deixe a lista vazia, senão o seu próprio push direto continua funcionando e o teste final não prova nada.

"Require branches to be up to date before merging" é o modo estrito: a branch do PR precisa estar atualizada com a main antes do merge. (Available rules) Ligue. Assim, os checks sempre rodam sobre o código que vai de fato para a main. O custo é às vezes clicar em Update branch.

Faça você

  1. Abra a tela. Em github.com/rafelms/EduRAG: Settings → Rules → Rulesets → New ruleset → New branch ruleset.
  2. Nome e status. Ruleset name: protege-main. Enforcement status: Active.
  3. Bypass list vazia. Não adicione ninguém.
  4. Alvo. Em Target branches → Add target → Include default branch.
  5. Regras. Confira se Restrict deletions e Block force pushes estão marcadas. Marque Require a pull request before merging com Required approvals = 0.
  6. Checks. Marque Require status checks to pass e Require branches to be up to date. Em Add checks, digite e adicione backend e frontend. Se aparecer a opção de origem, escolha GitHub Actions.
  7. Salve em Create.

Prove o portão

O plano diz: "Pronto quando: um PR com teste quebrado não consegue ser mesclado." Faça as duas provas e tire print de cada uma, como pede a seção "Comprovação para o currículo" do plano.

Prova 1: push direto é recusado

git switch main
git commit --allow-empty -m "teste: push direto"
git push origin main

O push precisa ser recusado, com uma mensagem do tipo Repository rule violations. Depois, desfaça o commit local com git reset --hard origin/main. Esse commit só existe na sua máquina, porque o push foi recusado.

Prova 2: PR com teste quebrado fica travado

git switch -c teste/portao-quebrado
# crie tests/test_portao.py com:
#   def test_portao():
#       assert False, "falha proposital para provar o portão"
git add tests/test_portao.py
git commit -m "teste: falha proposital"
git push -u origin teste/portao-quebrado

Abra o PR no GitHub. O job backend deve ficar vermelho e o botão de merge, bloqueado. Tire o print, feche o PR sem mesclar e apague a branch.

O fluxo novo, daqui para frente

Toda mudança agora segue o mesmo caminho: git switch -c <branch> → commit → push → PR → checks verdes → merge no GitHub → git switch main && git pull. A primeira mudança de verdade nesse fluxo é marcar a etapa 3 como feita no pipeline-plano.md (junto com esta pasta docs/estudo/).

Recupere da memória

Responda sem voltar ao texto. O esforço de lembrar é o que fixa o conteúdo.

1. Por que exigir 0 aprovações, e não 1?

2. Qual nome você digita em "Add checks"?

3. Você criou o ruleset, mas o push direto na main ainda funciona. Qual é a causa mais provável?

4. O que o modo "Require branches to be up to date" garante?
