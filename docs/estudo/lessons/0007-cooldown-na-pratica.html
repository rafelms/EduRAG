Cooldown na prática

Não aceitar uma versão no dia em que ela sai. Com números do seu próprio uv.lock.

Para que serve, em uma frase

Quando você roda uv lock --upgrade (ou o Dependabot abre um PR), a ferramenta pega a versão mais nova de cada pacote. A mais nova é também a menos examinada: ninguém ainda teve tempo de notar se ela veio com algo que não devia. O cooldown diz: "só aceito versões publicadas há pelo menos 7 dias". Se uma versão maliciosa for descoberta e removida nesse prazo, ela nunca chega ao seu lock.

Isso não é teoria. Em dezembro de 2024, quatro versões do pacote ultralytics (8.3.41, 8.3.42, 8.3.45 e 8.3.46) foram publicadas no PyPI com código malicioso, através da própria pipeline de publicação do projeto, que foi comprometida pelo cache do GitHub Actions. As quatro foram removidas. (PyPI: análise do ataque à ultralytics) A análise não diz quanto tempo elas ficaram no ar. Mas quem tinha cooldown só correria risco se elas tivessem ficado mais que o prazo.

Liga com o que você já fez: fixar actions por SHA (aula 0005) protege contra tag movida. O cooldown protege contra versão nova envenenada. Os dois são cadeia de suprimentos: o SHA trava o que você já confia, o cooldown atrasa o que você ainda não conhece.

O exemplo prático: o seu lock de hoje

Rodei uv lock --upgrade --dry-run (mostra o que mudaria, sem gravar) no seu uv.lock atual, com o uv 0.13.1 do Dockerfile, duas vezes: sem cooldown e com o corte de 7 dias valendo para hoje à tarde (30/10, 15:48).

O custo: a correção também espera

O exclude-newer do uv não distingue novidade de correção. Se amanhã sair uma correção de CRITICAL, o uv lock não a aceita por 7 dias, e o trivy-fs fica vermelho. Você viu isso com o certifi na aula 0005. O Dependabot distingue: o cooldown dele só está disponível para atualizações de versão, não de segurança. (Dependabot options reference)

SituaçãoO que fazer
Versão nova comumNada. Espera os 7 dias.
Correção de segurança com menos de 7 diasexclude-newer-package = { PACOTE = false } no [tool.uv], uv lock --upgrade-package PACOTE, e remover a isenção num PR depois que a versão completar 7 dias.
pyproject.toml exige um mínimo mais novo que o corteO uv lock falha (veja abaixo). Espere o prazo, ou não suba o mínimo.

Por que só depois das 15:48 de hoje

Rodei o cooldown hoje de madrugada, e o uv respondeu:

Resolving despite existing lockfile due to addition of global exclude newer 2026-10-23T04:24:58Z
error: No solution found when resolving dependencies
  cause: Because fastapi>0.161.1 was published after the exclude newer time and your project
  depends on fastapi>=0.162.0, we can conclude that your project's requirements are unsatisfiable.

O PR #24 do Dependabot subiu o mínimo para fastapi>=0.162.0, e essa versão saiu em 23/10 às 18:47 UTC. Até ela completar 7 dias (30/10, 15:47 em Brasília), não existe versão aceitável. Ou seja: o uv não rebaixa um mínimo, ele falha. É por isso que o cooldown vai também no dependabot.yml: para o bot não propor mínimos que o uv ainda não aceita.

E o uv sync --locked do Dockerfile?

O medo natural: se o corte "anda" a cada dia, o lock fica desatualizado sozinho e o build quebra. Testei adiantando o relógio do contêiner em 5 dias: o uv lock --upgrade passou a ver mais versões, mas o uv lock --check continuou passando. O lock guarda o prazo (exclude-newer-span = "P7D"), não a data. As versões travadas só mudam quando alguém roda uv lock --upgrade.

Branch ci/cooldown, criada a partir da main atualizada, depois das 15:48 de hoje. Dois arquivos.

  1. pyproject.toml: no [tool.uv], acrescente o cooldown de 7 dias. A sintaxe está na referência.
  2. Gere o lock. Esta máquina Windows não tem o uv; rode pelo Docker, com a mesma versão do Dockerfile: 
    docker run --rm -v "${PWD}:/w" -w /w python:3.12-slim sh -c "pip install -q uv==0.13.1 && uv lock"
  3. Aposte e confira: o que o git diff uv.lock deve mostrar? Depois rode. Se aparecer o arquivo inteiro como alterado, é quebra de linha (o contêiner grava LF): me avise antes de commitar.
  4. .github/dependabot.yml: no bloco uv, acrescente cooldown com default-days: 7. O uv é suportado; sem configuração, o padrão do Dependabot é 3 dias. (referência) Atenção à indentação: cooldown fica no mesmo nível de schedule.
  5. Experimento: rode o mesmo contêiner com uv lock --upgrade --dry-run e encontre a starlette. Até 31/10 às 12:04, ela deve ir para a 1.9.0, não para a 1.10.0.
  6. PR e checks. O imagem-api verde prova que o uv do Dockerfile lê o cooldown (uv sync --locked). Depois do merge, o alerta uv-missing-dependency-cooldown deve fechar sozinho em Security → Code scanning. Esse é o "pronto quando" da etapa 6: o Semgrep sem avisos de cadeia de suprimentos.
