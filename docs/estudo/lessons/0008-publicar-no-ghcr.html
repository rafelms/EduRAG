Publicar no GHCR

Só a main publica, só depois dos portões, e cada imagem leva o SHA do commit que a gerou.

Antes de começar (03/11): o trivy-fs está vermelho em qualquer PR até a pypdf 6.21.4 entrar pelo PR #38 (04/11, depois das 14:00). Você pode escrever, abrir e revisar o PR desta etapa agora; o merge espera o #38. Crie a branch a partir da main, não da ci/cooldown.

O que esta etapa faz

Até aqui, a imagem era construída, escaneada e jogada fora no fim do job (push: false). A etapa 8 guarda a imagem num registro: o GHCR (ghcr.io), o registro de contêineres do GitHub. É de lá que um servidor vai baixar a imagem para rodar. Na etapa 11, o mesmo papel passa para o ECR da AWS.

O "pronto quando" do plano: cada merge na main gera uma imagem rastreável até o commit. Rastreável quer dizer que, olhando a tag da imagem, você sabe exatamente qual código está dentro dela.

Decisão 1: publicar no mesmo job ou num job separado?

Steps a mais no imagem-apiJob novo publica-api com needs
Permissãopackages: write em todo PR, porque permissions não aceita ifpackages: write só no job que roda na main
Imagem publicadaExatamente a escaneadaReconstruída do cache gha: as camadas saem do cache, sem refazer nada
OrdemNatural (mesmo job)needs: imagem-api: só roda se o portão passou

Recomendo o job separado, por menor privilégio: o portão continua só lendo, e a permissão de escrita existe só onde é usada. O custo é a imagem publicada ser um segundo build. Por isso, há uma conferência no checklist: o log do build no publica-api deve mostrar CACHED em todos os passos. Se algum passo for refeito, a imagem publicada não é mais garantidamente a que o Trivy viu.

E por que confiar que a main passou em todos os portões, e não só nos do build.yml? Porque nada entra na main sem os checks obrigatórios, e a regra strict exige o PR atualizado com a main. O commit do merge tem o mesmo código que foi testado.

Aposte: num PR, o que acontece com o job publica-api? Aparece vermelho, verde, ou de outro jeito? E ele deve entrar nos checks obrigatórios do protege-main?

Resposta

Ele aparece como pulado (skipped), porque o if só é verdadeiro em push na main. E não entra no ruleset: um check que nunca roda em PR não prova nada sobre o PR.

Decisão 2: as tags

TagExemploPapel
SHA do commitghcr.io/rafelms/edurag-api:6448312… (40 caracteres)O endereço de verdade: um commit, uma imagem. É o que o deploy vai usar.
latestghcr.io/rafelms/edurag-api:latestSó um apelido para "a mais recente". Muda a cada merge.

O SHA está no contexto github.sha. (GitHub: Contexts) Várias tags vão na entrada tags da build-push-action, uma por linha (bloco | do YAML). O exemplo do GitHub usa a docker/metadata-action para gerar as tags. Aqui ela é dispensável: duas tags escritas à mão são uma action a menos para fixar por SHA e vigiar.

Armadilha do nome: o nome de uma imagem só aceita letras minúsculas. (Docker: image tag) O github.repository vale rafelms/EduRAG, com maiúsculas, e quebraria o push. Escreva o nome por extenso (ghcr.io/rafelms/edurag-api).

Para estudar (o plano pede): por que tag por SHA permite rollback e latest não? Pense na pergunta "qual imagem estava no ar antes do deploy quebrado?" e tente responder com cada uma das duas tags.

Resposta

Com o SHA, a resposta é o commit anterior da main: git log mostra qual é, e a imagem com aquele nome continua no registro. Com latest, não há resposta: a tag já aponta para a imagem quebrada, e a anterior ficou sem nome. A etapa 11 depende disso: "se o smoke test falhar, voltar para a tag anterior".

Mão na massa

Desta vez, sem esqueleto: na etapa 7 você escreveu os dois jobs certos de primeira. Se travar na estrutura, peça o esqueleto.

  1. Branch: git switch main; git pull; git switch -c ci/publica-ghcr.
  2. Job publica-api no build.yml, depois dos dois portões. needs aponta para o portão da mesma imagem. O if do job combina duas condições: o evento é push e a ref é a da main. Os nomes estão nos contextos github.event_name e github.ref; a ref da main é refs/heads/main. (GitHub: Workflow syntax)
  3. Permissões: contents: read e packages: write. Nada além disso.
  4. Steps: checkout, Buildx, login e build. O login é a docker/login-action, fixada por SHA (confirme a última versão no git ls-remote), com registry: ghcr.io e o usuário e a senha da seção acima.
  5. Build: mesmo context, push: true, as duas tags, e cache-from com o mesmo scope do portão. Pense: precisa de cache-to? Quem já escreveu esse cache?
  6. publica-front: copie e decida o que muda (mesmas pistas da aula 0006).
  7. Repare: as duas linhas env do PR #33 (DOCKER_BUILD_RECORD_UPLOAD e DOCKER_BUILD_SUMMARY) sumiram do build.yml no commit do #34. Decida se elas voltam, e em quais steps de build.
  8. Antes do push: me mostre o arquivo. Abra o PR: os dois publica-* devem aparecer como pulados. O trivy-fs estará vermelho até o #38 entrar; não é deste PR.
  9. Depois do #38: Update branch (o PR é seu), espere tudo verde e mescle.
  10. No run da main: os quatro jobs do Build rodam, os publica-* por último. No log do build de cada um, confira o CACHED. Em github.com/rafelms → Packages, as duas imagens devem aparecer com a tag igual ao git log -1 --format=%H da main.

Prove que a imagem publicada é a certa

O pacote nasce privado, e fica vinculado ao repositório automaticamente quando é publicado por um workflow. (GitHub: Container registry) Para baixar sem login, torne os dois pacotes públicos: na página do pacote, Package settings → Change visibility. O repositório já é público, e o .dockerignore exclui o .env. Mesmo assim, a decisão é sua.

docker pull ghcr.io/rafelms/edurag-api:<sha>
docker run --rm --entrypoint id ghcr.io/rafelms/edurag-api:<sha> -u

Esperado: 10001. É a mesma checagem do portão, agora na imagem que saiu do registro. Para provar o "rastreável", veja o próximo merge (qualquer PR) gerar uma tag nova, com o latest mudando de imagem e a tag antiga continuando lá.
