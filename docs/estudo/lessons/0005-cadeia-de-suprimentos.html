Aquecimento: retomada da aula anterior

Sem olhar a aula 0004: o git ls-remote devolveu duas linhas para a mesma tag. Qual você usa no uses:, e como saber, só pelo formato da linha? Se não lembrar, volte à seção Fixe por SHA, não por tag e anote a resposta; ela é a parte mais fácil de errar no PR 4.

Parte 1: PR 4, fixar as actions por SHA

O guia de segurança do GitHub recomenda fixar actions de terceiros num SHA de commit completo, e diz o que conferir: o SHA deve vir do repositório da própria action, não de um fork, e mesmo assim vale auditar o código. (GitHub: Secure use) A lista de tarefas é o seu relatório do Semgrep. Rode-o e anote os arquivos e as linhas:

uvx semgrep@1.180.0 scan --config p/default --metrics off --quiet

Na minha rodada de 22/10/2026 eram 10 usos de action por tag (regra github-actions-mutable-action-tag) mais 1 do uv (parte 2). Os 10 usos são 6 actions diferentes. Depois dos jobs da aula 0004, o seu número será maior: cada checkout novo conta.

  1. Branch nova a partir da main atualizada. Confira o * do git branch antes de editar.
  2. Para cada action: rode o git ls-remote --tags no repositório dela, filtrando pela tag que você usa hoje. Escolha a linha certa (aula 0004).
  3. As tags de versão maior (como v7) se movem a cada versão menor. Descubra qual versão exata aquele commit é: git ls-remote --tags <repo> | grep <sha> mostra os nomes de tag que apontam para ele. Escreva a versão exata no comentário: # v7.x.y.
  4. Troque o uses para repo@<sha-completo-de-40-caracteres> # vX.Y.Z. Um SHA abreviado não funciona.
  5. Não esqueça do upload-sarif (o caminho tem /upload-sarif depois do repositório) e das actions dos jobs novos da aula 0004.
  6. Rode o Semgrep de novo: os avisos de action devem sumir. Se um sobrou, o relatório diz a linha.
  7. Abra o PR. Todos os checks verdes provam que cada SHA existe e baixa a action. Um SHA errado faz o job falhar ao baixar a action.

Cuidado com a ordem dentro do PR: troque primeiro uma action e rode a CI. Se você trocar as 10 de uma vez e um SHA estiver errado, o erro aparece em vários jobs ao mesmo tempo e fica mais difícil achar qual foi.

Parte 2: cooldown no uv

O aviso restante, uv-missing-dependency-cooldown, aponta o [tool.uv] do pyproject.toml. A defesa: o uv só aceita versões publicadas há pelo menos N dias. A ideia (é raciocínio, não citação) é que pacotes comprometidos costumam ser detectados e removidos nas primeiras horas ou dias. A opção do uv se chama exclude-newer e aceita, além de data fixa, uma duração: 24 hours, 1 week ou 30 days. (uv: Settings) O mesmo documento descreve o exclude-newer-package, que aplica um corte diferente, ou nenhum, a um pacote.

Parece uma linha só. Mas eu testei antes, e a linha "só" tem duas armadilhas que o plano não prevê.

Armadilha 1: o Dockerfile

Com exclude-newer = "7 days" no pyproject.toml, o uv lock do meu uv local (0.13.1) funcionou e o Semgrep zerou o aviso. O lock ganhou 4 linhas, entre elas exclude-newer-span = "P7D". Mas o seu Dockerfile baixa o ghcr.io/astral-sh/uv:0.5, e esse uv leu o mesmo arquivo e respondeu:

failed to parse year in date "7 days": failed to parse "7 da" as year

O uv:0.9 e o uv:0.13.1 passaram dessa leitura (parei no passo seguinte, porque a imagem pura do uv não tem o resto do sistema para o sync). Sua tarefa: subir a versão do uv no Dockerfile e provar com docker build que a imagem do api continua construindo. Sem isso, o PR passa na CI atual (ela ainda não constrói imagens) e quebra só na etapa 7. Esse é um bom exemplo de por que o build da imagem vira portão mais adiante.

Armadilha 2: o cooldown desfaz a correção de segurança

Depois do PR 1, o seu uv.lock tem o certifi 2026.10.19, publicado em 19/10. Com cooldown de 7 dias, essa versão ainda é "nova demais". No meu teste, ao adicionar o cooldown sobre o lock já corrigido:

Resolving despite existing lockfile due to addition of global exclude newer 2026-10-15T…
Updated certifi v2026.10.19 -> v2026.7.22

O uv rebaixou o certifi para a versão vulnerável, a mesma que o Trivy marcou como CRITICAL. Aposte antes de seguir: o que a CI do seu PR 4 vai mostrar nesse caso? (O trivy-fs da aula 0004 está de pé.)

A resposta e as saídas (abra depois de apostar)

O trivy-fs fica vermelho: o portão pega o rebaixamento. É o motivo de fazer o scan primeiro e o cooldown depois. As saídas, em ordem de preferência:

  • Esperar: o certifi 2026.10.19 passa dos 7 dias em 26/10. Depois disso, o uv lock mantém a versão. Custa só o tempo.
  • Exceção: exclude-newer-package = { certifi = false } (testei: o uv lock --upgrade-package certifi volta para a 2026.10.19). Funciona, mas é uma isenção permanente num pacote, e é a de um pacote de segurança.
  • Reduzir o prazo (por exemplo, "3 days"): é um número a mais para você escolher, sem solução de fundo.

Não há saída correta única: é uma decisão sua, e a conta é risco de pacote malicioso novo × atraso em correção de segurança. Escreva a sua em duas linhas num comentário do pyproject.toml ou no PR.

O Dependabot já tem essa distinção embutida: a opção cooldown dele só está disponível para atualizações de versão, não de segurança. (Dependabot options reference) Ou seja: ele espera para o que é novidade, mas não espera para o que é correção. O exclude-newer do uv não distingue.

Parte 3: PR 5, o dependabot.yml

O Dependabot abre PRs de atualização, e é ele quem mantém atual tudo que você acabou de fixar. É um arquivo de configuração, não um job: vai em .github/dependabot.yml (não em workflows/). Os campos obrigatórios são version (sempre 2), updates, e, em cada item, package-ecosystem, directory (ou directories) e schedule.interval. (Dependabot options reference)

O que atualizarValor de package-ecosystemOnde está
Python (uv.lock)uv (a referência o lista; o pip é a alternativa)raiz do repositório
npmnpmfrontend/
Dockerdockerdois Dockerfiles: na raiz e em frontend/
Actionsgithub-actionsos workflows, em .github/workflows/

São quatro ecossistemas e cinco pastas no total. Quem usa o campo directory (singular) escreve um item por pasta; o directories (plural) aceita uma lista. Confirme na referência como o github-actions lê o directory, que eu não consegui confirmar no texto que li.

  1. Esqueleto: version: 2 e a lista updates:. Cada item da lista começa com - e tem package-ecosystem, directory e schedule com interval (a mesma regra do YAML dos workflows: o - abre o item, e as chaves do item ficam alinhadas).
  2. Um item por ecossistema/pasta da tabela acima. Comece sem opções extras e vá acrescentando só o que decidir.
  3. Frequência: escolha o interval (daily, weekly, monthly…). Pense em quantos PRs por semana você aguenta revisar sozinho.
  4. Ruído: open-pull-requests-limit (o padrão é 5 abertos por ecossistema) e groups (juntar atualizações menores num PR só) existem para isso. Decida se vale usar.
  5. Cooldown: a referência diz que o Dependabot já aplica 3 dias de cooldown a atualizações de versão mesmo sem configuração. Decida se muda o default-days.
  6. Abra o PR. O arquivo não roda como job, então a CI não o testa. Depois do merge, confira em Insights → Dependency graph → Dependabot se o GitHub leu o arquivo sem erro.

Quando abrir o primeiro PR do Dependabot (pode levar horas ou até a próxima janela do interval), repare em três coisas: ele passa pelos mesmos checks obrigatórios que o seu PR; nas actions fixadas por SHA, ele troca o SHA e o comentário de versão (a documentação do GitHub diz que atualiza o comentário que estiver na mesma linha); e a descrição do PR traz as notas de versão para você ler antes de mesclar. (GitHub: Secure use)

Um limite que fica registrado: o Dependabot não cria alertas para actions fixadas por SHA. (GitHub: Secure use) Ou seja, depois do PR 4, uma action fixada com falha conhecida não avisa sozinha: você depende dos PRs de versão do Dependabot. Por isso o SHA, sozinho, não basta.

Prove e feche a etapa

Duas coisas para guardar como evidência do currículo:

  1. O Semgrep em zero. Print da aba Security → Code scanning sem os avisos de cadeia de suprimentos (ou a saída do semgrep scan local, vazia). É a prova de que os 11 avisos viraram trabalho feito.
  2. O primeiro PR do Dependabot, com os checks rodando. Mescle um dele (de preferência o das actions), e guarde o link.

Decisão em aberto, para depois

Com o relatório zerado, o portão do Semgrep (--severity ERROR) pode passar a barrar também WARNING: assim, uma action nova por tag em um PR futuro seria barrada. O custo é qualquer aviso novo de outra regra também bloquear o merge. Pense nisso e traga uma opinião; não é obrigatório para fechar a etapa.

A etapa 6 está pronta quando o trivy-fs e o npm-audit são checks obrigatórios, o Semgrep não aponta mais cadeia de suprimentos, e o Dependabot abriu pelo menos um PR. Aí atualize o pipeline-plano marcando os itens, e a etapa 7 (build e scan das imagens) começa.
