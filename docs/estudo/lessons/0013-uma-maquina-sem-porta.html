Aula 0013 · Etapa 10 do pipeline-plano · ~90 min

Uma máquina sem porta

Um EC2 que ninguém alcança de fora e que você abre por um túnel do SSM. Com o tamanho escolhido por medida, e não por chute.

Fontes conferidas em 22/11/2026. Preços de us-east-2 tirados do arquivo público que alimenta a página de preços da AWS (publicado em 21/11/2026). Docs do provider lidos na tag v6.73.0.

O que muda no mapa: a interface do EduRAG e a RAM medida no EC2 dependem do docker-compose.prod.yml, que é da etapa 11. Nesta aula, o túnel é provado com um nginx de teste, e a RAM é medida na sua máquina antes de escolher o tamanho.

Aquecimento: de memória

Sem abrir nada: (1) qual comando mostra o que mudaria sem mudar nada? (2) Onde fica o .tflock e quando ele some? (3) Um SecureString criado pelo Terraform fica em texto puro onde? Confira na aula 0012.

O desenho

você (PowerShell)→aws ssm start-session→AWS Systems Manager←agente do SSM (sai pela 443)←EC2: nenhuma porta de entrada

Por que nenhuma porta de entrada funciona? Quem abre a conexão é o agente do SSM, de dentro para fora: "SSM Agent initiates all connections to the Systems Manager service in the cloud". Por isso a máquina não precisa aceitar conexão nenhuma. (SSM: VPC endpoints) O agente já vem instalado no Amazon Linux 2023. (AMIs with SSM Agent preinstalled)

Mas ele precisa de saída. O agente fala por HTTPS (443) com ssm, ssmmessages e ec2messages da região. (Session Manager prerequisites) E a instalação do Docker e o download das imagens também saem pela 443.

Armadilha: o Terraform apaga a saída padrão

Um security group criado pelo console nasce com uma regra que libera toda saída. Pelo Terraform, não: "Terraform will remove this default rule, and require you specifically re-create it if you desire that rule". (aws_security_group)

Aposte: se você criar o security group sem nenhuma regra de saída, o que acontece com a instância?

Resposta

Ela sobe, mas fica muda: o agente não alcança o SSM, então ela nunca aparece como Online e você não entra. O user_data também falha ao baixar o Docker. Por isso a aula pede uma regra de saída, só para TCP 443. O DNS da AWS não precisa de regra: "Security groups do not filter traffic destined to and from [...] Amazon Domain Name Services (DNS)". (Security groups)

A documentação recomenda regras como recursos separados (aws_vpc_security_group_egress_rule), e não blocos egress dentro do grupo. Não misture os dois jeitos. (aws_security_group, notas no topo)

Por que um IPv4 público, se ninguém entra?

Para a instância sair. A VPC padrão já tem "a public subnet in each Availability Zone, an internet gateway". (Default VPCs) A alternativa sem IP público são os VPC endpoints do SSM (três, obrigatórios) (SSM: VPC endpoints), que cobram por hora cada um. O exemplo da página de preços usa US$ 0,01 por hora por ENI (PrivateLink pricing). Ou seja, uns US$ 0,03 por hora, contra US$ 0,005 do IPv4. E sem internet, o Docker não baixa nada do GHCR. O IP público fica, e é o security group que fecha a porta.

Como decidir: no passo 2, você mede a RAM da stack rodando no Docker Desktop. Some a RAM dos contêineres, deixe espaço para o sistema e para o Prometheus e o Grafana (etapa 13), e escolha. A escolha é sua.

O user_data: o primeiro boot

"By default, user data scripts and cloud-init directives run only during the boot cycle when you first launch an instance." Roda como root ("do not use the sudo command in the script"), precisa começar com #! e deixa o log em /var/log/cloud-init-output.log. (EC2: user data)

O script infra/user_data.sh tem quatro tarefas:

  1. Instalar o Docker pelo dnf (o pacote docker do AL2023) e ligar o serviço com systemctl enable --now.
  2. Criar /usr/local/lib/docker/cli-plugins. É onde o Docker procura o plugin do compose para todos os usuários. (Docker: install the plugin manually)
  3. Baixar o docker-compose-linux-x86_64 de uma versão fixa para lá, com o nome docker-compose.
  4. Conferir o SHA256 antes do chmod +x. Se não bater, o script para (set -euo pipefail no topo).

Por que baixar à mão? Os repositórios padrão do AL2023 não trazem o plugin do compose. (HashiCorp Support: Docker on AL2023) E baixar binário da internet é cadeia de suprimentos: versão fixa e hash conferido, como na aula 0005. Pelo seu cooldown de 7 dias, a versão é a v5.7.1 (11/11). A v5.7.2 e a v5.8.0 saíram em 17/11.

Armadilha do Windows: o seu git está com core.autocrlf = true. Um .sh salvo com CRLF chega ao Linux como /bin/bash\r e não roda. Crie um .gitattributes na raiz com *.sh text eol=lf e confira no canto do VS Code se o arquivo está em LF.

Mão na massa

Sem esqueleto. Cada bloco tem o link da documentação. Se travar, peça o esqueleto sem valores.

  1. Sessão e branch: aws login --profile edurag (se venceu), $env:AWS_PROFILE = "edurag", aws sts get-caller-identity. Depois, git checkout main, git pull, git checkout -b infra/ec2.
  2. Medir a RAM, na sua máquina: docker compose up -d --build (sem nome de serviço), envie um PDF e faça uma pergunta na interface, para o Ollama carregar o nomic-embed-text. Depois rode docker stats --no-stream --format "table {{.Name}}\t{{.MemUsage}}". Anote cada contêiner e a soma. Por fim, docker compose down.
  3. Escolher o tipo: confira os elegíveis com aws ec2 describe-instance-types --filters Name=free-tier-eligible,Values=true --query "InstanceTypes[].[InstanceType, MemoryInfo.SizeInMiB, ProcessorInfo.SupportedArchitectures[0]]" --output table. Compare com a sua soma e escolha. Confira também que a VPC padrão existe: aws ec2 describe-vpcs --filters Name=is-default,Values=true --query "Vpcs[].VpcId".
  4. infra/rede.tf: o data "aws_vpc", o aws_security_group sem entrada e uma aws_vpc_security_group_egress_rule para TCP 443 em 0.0.0.0/0.
  5. infra/iam.tf: a política de confiança (aws_iam_policy_document), a aws_iam_role, o aws_iam_role_policy_attachment com o ARN da AmazonSSMManagedInstanceCore e o aws_iam_instance_profile. Use nomes que começam com edurag-.
  6. .gitattributes e o hash do compose: crie o .gitattributes (*.sh text eol=lf). Pegue o hash publicado: gh api repos/docker/compose/releases/tags/v5.7.1 --jq ".assets[] | select(.name == \"docker-compose-linux-x86_64\") | .digest".
  7. infra/user_data.sh: as quatro tarefas da seção acima. Na conferência, use sha256sum -c com uma linha <hash> <caminho> (dois espaços).
  8. infra/ec2.tf: o aws_instance com os argumentos da tabela (e o credit_specification, se for T3). Crie também infra/outputs.tf com dois output: o id e o public_ip da instância.
  9. terraform fmt, validate e plan: quantos recursos ele vai criar? (Conte os blocos resource antes de olhar.) No ami, o plano mostra o resolve:ssm:... ou um ID ami-...?
  10. terraform apply: a partir daqui, a hora está correndo. Anote os dois outputs e guarde o ID: $id = terraform output -raw instance_id (use o nome que você deu ao output).
  11. A máquina chamou a AWS? Depois de um ou dois minutos: aws ssm describe-instance-information --query "InstanceInformationList[].[InstanceId, PingStatus, AgentVersion]" --output table. Precisa aparecer Online. Se não aparecer em 5 minutos, volte à regra de saída e ao instance profile.
  12. Entrar sem SSH: aws ssm start-session --target $id. Lá dentro: cloud-init status --long, docker --version, docker compose version, free -m e df -h /. Se o compose não existir, leia sudo tail -50 /var/log/cloud-init-output.log.
  13. O túnel: ainda na sessão, suba um nginx de teste preso ao localhost da máquina: sudo docker run -d --name teste -p 127.0.0.1:8080:8080 nginxinc/nginx-unprivileged:alpine. Saia (exit). No Windows: aws ssm start-session --target $id --document-name AWS-StartPortForwardingSession --parameters portNumber="8080",localPortNumber="8080". Abra http://localhost:8080 no navegador. Depois, Ctrl+C no terminal. (Start a session: port forwarding, exemplo de Windows)
  14. O nmap de fora: com o IP público do output: docker run --rm instrumentisto/nmap -Pn --top-ports 1000 <ip>. O -Pn é preciso porque a máquina não responde nem ao ping. Espere ver as 1000 portas como filtered, nenhum open. A própria porta 8080, que tem o nginx, não aparece aberta.
  15. terraform destroy: leia o plano (o mesmo número de recursos do passo 9) e confirme. Depois, aws ec2 describe-instances --filters Name=tag:Projeto,Values=edurag --query "Reservations[].Instances[].State.Name" precisa dizer terminated.
  16. O PR infra/ec2: git status deve listar os .tf novos, o user_data.sh e o .gitattributes. Nada de .terraform/ nem de state. Commit e PR.
