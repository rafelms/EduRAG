Segredos e gitleaks

Segredo vazado: a ordem

  1. Revogar ou trocar a chave no provedor. Ela já é considerada comprometida.
  2. Conferir os logs de uso do serviço, para ver se alguém usou a chave.
  3. Só então decidir se vale reescrever o histórico (exige force push, e o ruleset bloqueia).

Apagar num commit novo não resolve: o commit antigo continua no histórico e em todo clone.

Varredura local do histórico

docker run --rm -v "$PWD":/repo:Z ghcr.io/gitleaks/gitleaks:v8.30.1 \
  git /repo --log-opts="--all" --redact -v
echo $?   # 0 = limpo · 1 = achado ou erro
Comando / flagUso
git <caminho>Analisa o histórico Git (via git log -p)
dir <caminho>Analisa arquivos, sem histórico
stdinAnalisa o texto da entrada padrão
--log-opts="..."Repassa opções ao git log (--all, intervalos)
--redactEsconde o valor do segredo na saída
-vMostra cada achado
-f sarifRelatório em SARIF (a aba Security usa esse formato; ver etapa 5)
detect / protectComandos antigos, descontinuados na v8.19.0

Falso positivo

  • Arquivo: .gitleaksignore na raiz, um Fingerprint por linha (commit:arquivo:regra:linha), com um comentário # explicando o motivo.
  • Na linha: comentário gitleaks:allow. Use pouco, porque qualquer pessoa pode escrever.

O que a action analisa: num PR, só os commits do PR; num push, só os commits enviados. O histórico antigo é responsabilidade da varredura local.

Prova de bloqueio

echo "AWS_ACCESS_KEY_ID=AKIA$(tr -dc 'A-Z2-7' </dev/urandom | head -c16)" > config-falsa.env

Nunca use AKIAIOSFODNN7EXAMPLE: a regra aws-access-token tem uma exceção para valores que terminam em EXAMPLE.

Quando algo dá errado

SintomaCausa provável
Docker: permission denied ao ler /repoFaltou o :Z no volume (SELinux do Fedora)
dubious ownership no containerO dono da pasta é diferente do usuário do container: rode o binário do gitleaks direto, sem Docker
